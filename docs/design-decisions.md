# 设计决策（青枢出行 · Anti-AI-Silo）

> **地位**：架构级 ADR 集合；与 [BLUEPRINT.md](../BLUEPRINT.md) 配套。  
> **版本**：V2.1 · 2026-08-07  
> **范围**：只定原则与取舍；不写 UI 交互稿。

---

## DD-01 · 成品定义：Loops + Tools + Skills

**决策**：企业 AI 可治理成品拆成三件套——平台控制环、平台工具、部门 Skill。

**理由**：转型交付物若说成「上了几个 Agent」，对象不可审计（人设/Prompt/私有脚本混杂）。三件套分别对应：认知执行模式、可批准的副作用边界、业务差异配置。

**后果**：Demo 讲解与文档主轴改为平台治理面；「部门 Agent」不再作为架构一等公民。

---

## DD-02 · 反孤岛靠平台管环与工具，不靠共用 Agent

**决策**：防 AI 孤岛 = 统一发版/白名单/共享资产；**不是**「全公司共用一个或几个 Agent」。

**理由**：共用 Agent 仍会在各部门复制 Prompt、复制数据访问、复制「半套环」。重复发生在环与手脚，不在「Agent 名字是否共用」。

**后果**：业务视角按部门浏览 **Skill** 并试跑；**技术运维视角**看运行态（日志 / 指标 / 链路 / 共享产出健康），**不是**再做一张「按环查规章 / 试跑 RAG」的业务墙副本。

---

## DD-03 · 平台控制环收敛为 4（Retrieve / Act / Extract / Plan）

**决策**：平台主清单只保留四环；旧六类中的 Rule+LLM、Vision 降为子模式或扩展位。

| 环 | 解决什么 | 不解决什么 |
|----|----------|------------|
| Retrieve | 长文知识问答与引用 | 多步写库、硬闸门 |
| Act | 多步工具闭环 | 纯 schema 抽取、战役编排主控 |
| Extract | 结构化抽取与校验 | 开放域闲聊、复杂规划 |
| Plan | 读共享后的闸门/多步计划/组合 | 替代 ToolRegistry |

**理由**：四环覆盖咨询故事与现仓已落地能力；六类清单稀释「平台管什么」的记忆点。

**后果**：`agents/rule_llm/`、`agents/vision/` 可留作扩展，**不**进入平台主验收清单。Plan 环是平台叙事闭环所必需（Story2）。

---

## DD-04 · 工具治理轴为 3 类（Read / Knowledge / Write-Govern）

**决策**：平台工具台账主分类为三类；业务域（service/channel…）降为次级标签。

**理由**：治理要回答「谁能读主数据 / 谁能搜知识 / 谁能写共享与触达」。按业务域分类便于开发检索，但不构成平台治理语言。

**后果**：catalog/文档展示优先三类；handler 实现不必物理拆目录，可用 `category` 或映射表归类。

---

## DD-05 · 业务差异只进 Skill，禁止复制环与 DataFetcher

**决策**：部门差异（目标、语气、白名单、schema/索引）只存在于 `skills/`；各环目录禁止私有 `data_fetcher` / 私有 tool 实现。

**理由**：这是去重与治理的同一条线：环与手脚变更一次，全公司 Skill 受益。

**后果**：新部门 = 新 Skill（或改 YAML），不是新 Agent 工程。

---

## DD-06 · 跨功能只经共享产出；禁止 Agent 互聊与管道接力

**决策**：功能 A 与功能 B 若有关系，只通过 `AIOutput` / 标签 / schema；**两次独立运行**。不做 Agent 对话总线，不做「上环跑完自动交给下环」。

**理由**：互聊/管道慢、难治理；共享资产可审计、可阻断（Story2）。

**后果**：`department_flows` 是 **关系说明书**（谁写过什么、谁可能读），不是联跑引擎。Planning 文档讲 Plan **Skill** 与依赖说明，不讲 Agent 聊天编排。

---

## DD-07 · 不做企业级单 Orchestrator

**决策**：多环并存；禁止一个中心编排器调度所有部门/所有 Skill。

**理由**：单 Orchestrator 易滑向「万能大脑」，与咨询反模式冲突，且实现过重。

**后果**：入口永远是 `control_loop + skill_id`；一期不自动联跑多 Skill。

---

## DD-13 · 双页面职责切开（业务试跑 ≠ 运维排查）

**决策**：

| 页面 | 受众 | 做什么 | 不做什么 |
|------|------|--------|----------|
| `/business` | 业务部门 | 一卡一功能一 Skill 试跑 | 当监控台 |
| `/ops` | 技术运维 | 故障排查看板：健康分 / 黄金指标 / 事件关联 / 根因 / **四环子页** / 调用链 | 当规章制度查询或第二套 Skill 墙 |

**理由（纠偏）**：早期把运维台设计成「按 agent_type 分治试跑 Skill」，结果运维页变成业务能力台（尤其 Retrieve 像规章问答），与 IT 故障排查目标错位。

**后果**：Skill 试跑只留在业务墙（及 CLI/API）；运维台消费 `run_logs` / `ai_outputs` / 健康指标；`/ops/embed` 嵌入的是排查面板，不是 RAG 试跑器。

---

## DD-12 · 一功能一 Skill（运行时）

**决策**：每种业务功能对应一个 Skill；用户/API 一次只跑一个 `skill_id` 直至终答。功能所需多步工具调用发生在 **同一 Skill + 同一控制环** 内（如 Act 的 think→act→observe）。

**理由**：与「不需要上个 Agent 做完给下一个 Agent」一致；交付物可清点、可授权、可评测。

**后果**：

- **不需要**为「取消 Agent 接力」而重写现有 Skill YAML（`fill_ticket`、`ticket_fields`、`repair_kb` 等已是完整功能）。  
- `ticket_fields` 与 `fill_ticket` 是 **两个可选功能**（纯抽取 vs 多步填单），不是必须串成的 Agent 管道。  
- Story2 = 再跑一个 `renewal_plan` 功能读共享层，不是 Plan Agent 与客服 Agent 对话。

---

## DD-08 · 协作层 Demo 降配

**决策**：`run_id` + 步骤日志 + 本地 store；不做分布式锁、消息队列、真 SSO。

**理由**：作品集证明「共享产出可跨环消费」即可；分布式协作是另一课题。

---

## DD-09 · 数据与品牌边界

**决策**：全合成数据；品牌统一为青枢出行；禁止真实客户名、合同、真实工单/录音入库。

**理由**：作品集合规与可公开 GitHub。

---

## DD-10 · 验收故事线不可砍

**决策**：

1. **Story1**：Skill 经 Write/Govern 写出 `AIOutput`  
2. **Story2**：另一次运行 Plan Skill（如 `renewal_plan`）读共享标签并阻断错误触达  

**理由**：无 Story2 则「反孤岛」只是口号。

---

## DD-11 · 表述边界

**可写**：虚构企业下的平台化 Loops+Tools+Skills 参考实现与录屏。  
**不可写**：已上线企业 AI 中台 / 多部门生产交付。
