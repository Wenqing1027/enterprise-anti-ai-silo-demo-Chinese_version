# ReAct Agent · 模块一：背景 + 跨部门功能 + 语气

> **喂食核心 · 模块一**（对应蓝图 `agents/react/`）  
> 虚构企业：**青枢出行（Qingshu Mobility）** · 智能电动车出行  
> 原则：多部门共用 **同一套 ReAct 控制环 + Tool/DataFetcher**；部门差异只进 **Skill（功能目标 + 语气）**  
> 版本：V1.0 · 2026-08-02

---

## 1. 背景

### 1.1 企业与 Demo 定位

青枢出行是虚构的智能电动车出行企业。各部门原先容易各自搭 Agent、各自复制数据访问，形成 **AI 孤岛 ≈ 数据孤岛**。

本 Demo 的 ReAct Agent 不是「按部门各建一套大脑」，而是：

| 轴 | 做法 |
|----|------|
| 技术类型 | 唯一一套 **think → act → observe** 控制环 |
| 业务差异 | 挂多个 **Skill**（填单、查主数据、渠道经营、写共享产出…） |
| 反孤岛 | 共用 Tool / DataFetcher / 标签字典 / `AIOutput` |

### 1.2 为什么这块用 ReAct

ReAct 适合 **多步工具调用与观察闭环** 的场景，例如：查客户 → 查车辆 → 查未结工单 → 生成工单草案 → `write_ai_output`。

不适合单独用 ReAct 包办的（留给其他大脑）：

| 类型 | 典型能力 |
|------|----------|
| RAG | 纯知识问答（维修/政策/制度长文） |
| Planning | 多日续费战役、周报编排 |
| Extraction | 纯结构化抽字段 |
| Rule+LLM | 硬规则闸门（续费分流、政策档位） |
| Vision | 巡检图 / 质检图 |

### 1.3 模块一产出用途

本模块定义 **谁（部门）需要什么能力、用什么口气说话**，供后续模块直接喂食：

| 后续模块 | 吃本模块什么 |
|----------|--------------|
| 模块二 · 工具箱 | 按下方功能挂 tools |
| 模块三 · 工作流 / System Prompt | 把「功能目标 + 语气」写进 Skill prompt 槽 |
| 模块四 · 安全边界 | 对敏感部门话术加硬限制 |
| 模块五 · 界面 / API | 按部门入口展示对应 Skill |

## 2. 跨部门功能清单（ReAct 轴）

> 口径：只列需要 **查工具 / 多步闭环** 的能力；纯 RAG / 纯 Vision 等不进本表。  
> 功能ID 对齐 `docs/AI功能需求清单.md`。

| **IoT / 车机** | telemetry 主动服务 | 查告警/里程→建议动作→写产出 | F-IOT-003 | △ 示意 |

### 2.2 跨部门共用能力（反孤岛显式项）

| 能力 | 涉及部门 | 目的 | Skill / Tool |
|------|----------|------|--------------|
| 主数据综合查询 | 服务 / 运营 / 战区 / 用户运营 | 同一套客户·车·单·工单 ID | `crm_lookup` |
| 共享产出写入 | 全部门（服务先写） | 产出资产化，供他 Skill 订阅 | `write_ai_output` / `shared_write` |
| 共享标签/产出读取 | 用户运营 / 渠道 / 管理层 | 跨 Skill 消费，阻断错误触达 | `read_ai_outputs` / `read_shared_tags` |
| 能力目录检索 | 全部门 | 发现已有 Skill，避免重复造 Agent | `list_capabilities` |
| 渠道经营查询 | 渠道 / 战区 / 零售质检消费方 | 经营与合规同一数据源 | `channel_ops` |

### 2.3 一期必跑映射（验收）

| Story | Skill | 部门叙事 | 反孤岛点 |
|-------|-------|----------|----------|
| Story 1 | `fill_ticket` | 服务填单 | 写入 `AIOutput` |
| Story 2 | `renewal_plan`（Planning）读服务产出 | 用户运营续费 | 未结投诉标签 → **阻断触达** |

## 3. 语气与风格（按部门）

> 风格写在 **Skill prompt 槽**，不写进 ReAct 控制环代码。  
> 标签名简洁，便于模块三直接引用。

| 部门 | 风格标签 | 语气要点（3 条内） | 禁用 |
|------|----------|-------------------|------|
| **服务事业部** | **稳妥确认型** | 先复述问题；短句确认事实；给可执行下一步 | 超权承诺「一定能修好/必赔」 |
| **用户运营 / App** | **促而不逼型** | 利益点清晰；一句一问；高敏立刻降档 | 恐吓式催费；无视投诉硬推 |
| **运营 · 订单/政策** | **口径严谨型** | 先给可执行建议；再附政策依据；不确定标「待人工」 | 编造返利数字 |
| **四大战区** | **前线干脆型** | 结论在前；动作编号列出；少形容词 | 长篇安抚、空话激励 |
| **渠道处** | **经营看板型** | 数字 + 异常点 + 下一步；语气中性 | 人身评判经销商 |
| **新零售** | **货架导购型** | 成交导向；缺货立刻给替代或到店路径 | 虚假库存、虚假活动价 |
| **采购平台** | **节点追踪型** | 时间点明确；催办礼貌强硬 | 甩锅供应商/内部同事 |
| **数据研究院** | **结论优先型** | 先答数；再给口径与限制；无数据就说无 | 臆造指标 |
| **人资管理平台** | **友好中立型** | 制度原文优先；敏感题引导 HRBP | 编造福利/薪资口径 |
| **IoT / 车机** | **告警简报型** | 严重度 → 现象 → 建议动作；三行说完 | 恐吓用户；过度技术黑话 |
| **系统/共享层**（写读产出） | **中性系统腔** | 只描述资产与状态，不扮演业务人 | 客服安抚腔、电销促销腔 |

### 3.1 Skill ↔ 风格落点（一期）

| Skill | 主责部门 | 风格标签 |
|-------|----------|----------|
| `fill_ticket` | 服务事业部 | 稳妥确认型 |
| `crm_lookup` | 多部门共用 | 结论优先型（少寒暄） |
| `channel_ops` | 渠道处 | 经营看板型 |
| `shared_write` / 读共享标签 | 全部门 | 中性系统腔 |
